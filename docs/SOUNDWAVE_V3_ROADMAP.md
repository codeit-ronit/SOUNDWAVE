# SoundWave V3 — implementation roadmap

Baseline: [M0 audit](SOUNDWAVE_V3_AUDIT.md), 7 November 2026, inspected commit `94c6e74` and verified test correction `6e49ceb`. This document is a plan, not a claim that the proposed capabilities exist. M0 is complete. **M1.2 is now implemented and verified on `feature/m1-private-playlists`; it has not been pushed or deployed.** M6.1 has also been implemented early and locally verified; a real GitHub Actions run remains pending, so its milestone status is partial. [CI evidence](CI.md). M1.1 is now implemented and locally verified; see [profile/settings evidence](M1_SETTINGS.md). M1.3 is now locally implemented and verified; see [queue semantics and evidence](M1_QUEUE.md). Other milestones remain planned. [M1.2 report](M1_PLAYLISTS.md).

## Delivery constraints and sequencing

Retain React/Vite, Express, PostgreSQL, optional SQLite compatibility, Redis, BullMQ and the PostgreSQL outbox. Keep one modular application with separately runnable API/worker processes. Reuse working authentication, favorites, progress, streaming, downloads and analytics; do not replace them with a new framework or introduce microservices.

Each numbered task is a reviewable vertical slice with a rollback/degradation path. Schema changes must be additive, checksum-versioned and tested on a fresh database and an existing populated fixture. Private collections must use the authenticated owner, bounded pagination and no shared caching. Public visibility changes must invalidate discovery caches. Do not silently drop SQLite support; either provide compatible migrations/tests or propose an explicit support-policy change first.

**Priority:** P0 = prerequisite/correctness or release gate; P1 = core product value; P2 = optional polish/advanced capability. Priorities apply to the associated release, not a demand to implement the entire document immediately. **Difficulty:** S = small change, M = bounded vertical slice, L = multi-component workflow, XL = several slices/operational uncertainty. These are relative sizes, not promised dates.

**Status:** Done = verified at its documented checkpoint; Partial = reusable behavior exists but acceptance criteria are not met; Missing = not implemented; External = provider/owner action is needed. A milestone is complete only when its required tasks and regression gate pass. Task numbers indicate grouping, not a prohibition on prerequisites: bring M3.1/M3.2 contract/bounds rules into new M1 endpoints, and M3.3/M3.4 correctness/authorization gates into M2 **before any creator functionality is exposed**. Public deployments require explicit approval.

Dependency path: M0 → small M1 listener slices → M2 creator/storage/publishing → M3 consolidated correctness/security gate → M4 measured operations → optional M5 discovery → M6 approved presentation/release. CI in M6.1 should be brought forward early; its label is not a reason to defer baseline automation.

## Smallest M1 deliverable

**M1.2 delivered: private named playlists, end to end.** The following scope is retained as its acceptance record; [actual implementation/results](M1_PLAYLISTS.md) meet it. It adds visible listener value and demonstrates relational modeling, owner authorization and transactions without adding infrastructure or touching audio delivery. Favorites remain their existing single library; playlists are additional named collections.

First slice:

1. Add `playlists` (UUID ID, authenticated owner FK, bounded name, created/updated timestamps) and `playlist_items` (playlist/story FKs, unique membership, stable insertion order). Add owner/recency and membership lookup indexes. Keep client IDs from selecting the owner. Give registered and isolated guest sessions the same current listener rules; preserve playlists on guest upgrade. Use compatible additive migrations, likely PostgreSQL `009_playlists.sql` and SQLite `010_playlists.sql` after confirming the migration head at implementation time.
2. Add private REST list/create/get/rename/delete and add/remove-story operations. Specify paths/response/error contracts before implementation; default list limit 20, maximum 50; cap a list at a documented small membership count, initially 100. Ownership mismatches should have a consistent non-disclosing response. Apply CSRF, existing shared limits and transactional mutation validation; do not put playlist payloads in the public Redis cache.
3. Add a small playlist view reachable from My Library plus create/rename/add/remove states using existing cards/dialog styling. No UI redesign, public sharing, collaborators, reordering, custom covers, queue editing, creator roles or recommendation changes in this slice.
4. Test create/rename/delete/membership, duplicate additions, non-existent stories, invalid/oversized names, max size/page bounds, forged owner, guest upgrade, rollback and independent users on both adapters. Browser: create → add story → refresh → logout/login → contents retained; second browser has no access; playback/favorites/downloads remain working.

**Completion gate:** all new contract/integration tests plus existing 153-test baseline (expanded as needed), production build/format, targeted playlist browser flow and existing core auth/player/offline regression suites pass. Commit the schema/API/UI slice in reviewable verified steps. Report results and residual issues; do not deploy it until approval. The exact test total must be recalculated, not copied from M0.

## What to defer

Do not add Kafka, Kubernetes, Elasticsearch, a service mesh, event-sourced rewrites, a separate auth service or a GPU model server. PostgreSQL FTS, existing outbox/BullMQ and one worker are sufficient until evidence shows a limitation. Run one local Compose stack on the 8 GB Mac; keep media processing concurrency low, avoid loading large model weights in the API, and run load/fault tests sequentially with disposable fixtures. Current scrypt can consume substantial memory for two parallel derivations; use bounded auth load rather than interpreting expected overload 503s as a reason to weaken hashing.

No claims of production scalability, real user counts, creator adoption, engagement uplift, always-on free workers, global CDN ownership, exactly-once email or cross-browser compatibility are supported by this roadmap. Those require implementation and evidence appropriate to the claim.
