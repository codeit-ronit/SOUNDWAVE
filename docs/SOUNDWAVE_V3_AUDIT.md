# SoundWave V3 — M0 repository audit

Audit date: **7 November 2026, Asia/Kolkata**. Inspected baseline: **`94c6e74`**. Verified test-only correction: **`6e49ceb`**. This is an inventory and planning checkpoint, not a production-readiness certification. No application feature, database migration or public deployment was introduced in M0.

**Assessment:** SoundWave is a working listener demo with substantive backend engineering. PostgreSQL, sessions, Redis, background work, byte-range streaming and offline playback are real implementations. It is not yet a creator platform. The largest gaps are product workflows, contracts/pagination, creator authorization/storage, CI, and operational visibility/durability. Preserve the modular monolith and build small vertical slices.

## Evidence and classification

The audit inspected tracked application/configuration files, both migration directories, all test files, scripts and existing reports. Generated audio was exercised through playback/streaming rather than interpreted as source code. Secrets and production database records were not read. Existing reports are historical evidence, not substitutes for rerunning checks.

- **COMPLETE AND VERIFIED:** the stated bounded capability is implemented and passed relevant checks in this audit. This does not imply that the wider subsystem is mature.
- **IMPLEMENTED BUT NEEDS HARDENING:** working implementation with specific correctness, operational or security limits below.
- **PARTIALLY IMPLEMENTED:** only part of the requested product behavior exists.
- **NOT IMPLEMENTED:** no matching route/schema/component/handler found.
- **BLOCKED:** completion requires an external prerequisite unavailable to this audit. Missing code alone is not a blocker.

Machine-readable results and log fingerprints: [m0-verification.json](m0-verification.json). Actual fresh HTTP measurements: [m0-http-load-results.json](m0-http-load-results.json). Implementation work is organized in [SOUNDWAVE_V3_ROADMAP.md](SOUNDWAVE_V3_ROADMAP.md).

## 3. Data model, migrations and concurrency

**Classification: IMPLEMENTED BUT NEEDS HARDENING.** PostgreSQL is genuinely the default persistence layer, not an unused dependency. `connectDatabase()` requires a URL unless SQLite compatibility is explicitly selected; production SQLite requires an explicit exception. [database/index.js](../server/database/index.js), [adapter.js](../server/database/adapter.js).

Eight PostgreSQL migrations / nine SQLite migrations are versioned and checksum-checked. PostgreSQL uses a transaction and advisory migration lock; SQLite also preserves legacy data with migrations/triggers. Fresh/concurrent migration and repeatable read-only SQLite-import tests passed. No destructive migration was made in M0. SQLite starts from the legacy core schema in [db.js](../server/db.js), so its migration count alone does not describe the entire schema.

There are **18 manifest-covered tables**, including migration bookkeeping. Indexes cover lowercased genre, favorite/progress recency, event owner/time/order and owner/story, session owner/expiry, job readiness/leases/owner, token owner/purpose/expiry, source refresh and challenge expiry. No title/full-text search index or creator/playlist relations exist.

The small SQL adapter binds values separately and allowlists SQL sort expressions. Transactions pin a connection through AsyncLocalStorage; nested calls reuse that transaction, not savepoints. PostgreSQL progress advisory locks serialize owner/chapter writes. Favorites/events/outbox, completion transitions, guest upgrades, recovery, Google exchanges, catalog imports and media writes have actual transactional behavior. Worker claims use `FOR UPDATE SKIP LOCKED` and fenced lease tokens. Regression tests exercise rollback, parallel completions, stale writes, unique races and cross-user isolation.

Remaining gaps: independent devices use last-arriving writes, some DB invariants (progress versus chapter duration) live at the API boundary, no production role separation, startup seeding always refreshes the revision and rewrites bundled catalog fields, and the migration runner splits trusted SQL on semicolons (not suitable unchanged for SQL functions with embedded semicolons). New creator writes must never be overwritten by startup seeding. There is no controlled expand/contract deployment migration stage or concurrency/load proof beyond the recorded tests.

## 4. Authentication, authorization and security

**Classification: IMPLEMENTED BUT NEEDS HARDENING.** Sources: [auth middleware](../server/middleware/auth.js), [identity repository](../server/repositories/identity.js), [auth service](../server/services/auth.js), [passwords](../server/services/passwords.js), [Google verifier/service](../server/services/google.js), [recovery](../server/services/accountRecovery.js), [HTTP middleware](../server/middleware/http.js), [config](../server/config.js).

- Scrypt passwords use fixed `N=131072,r=8,p=1`, random salts and timing-safe comparison. At most two expensive derivations per process; excess returns 503. Passwords are not encrypted/plaintext.
- Random 256-bit session secrets are stored only as SHA-256 hashes; absolute expiry, rotation and logout revocation are DB-backed. Production cookies are `__Host-`, Secure, HTTP-only, SameSite=Lax, Path=/ with no Domain. CSRF tokens plus Origin/Fetch Metadata checks protect writes.
- Google uses fixed Google JWKS, signature/issuer/audience/time/nonce/email/authorized-party checks. Single-use hashed nonce, identity uniqueness/locks, explicit linking, no retained Google token/secret. Google-only recovery remains with Google.
- All current private data resolves ownership from the cookie, never a client user ID. `X-Session-User` only rejects stale tabs. Account changes reset private player/library state and notify tabs. Test-only middleware/verifier injection requires constructor access; no public bypass header/environment switch was found.
- Verification/reset tokens are hashed, expiring and single-use; reset revokes sessions. Encrypted mail payloads use AES-GCM. SMTP is at least once; internet delivery is not verified and is disabled in the public demo.
- Parameter binding, ID/body limits, 8 KB JSON cap, allowed sorts/types, bounded errors, exact configured CORS, safe file mappings, provider host validation and React text escaping are implemented/tested. No `dangerouslySetInnerHTML` or arbitrary HTML rendering was found in application UI.
- Bounded tracked-file scan found no private-key/common AWS/GitHub/live-secret patterns in 182 baseline tracked files; only `.env.example` is tracked. This was not an all-history or comprehensive secrets scan. Clean Node 22 `npm ci` reported **0 known vulnerabilities**, which is not a security assessment.

Gaps: no creator/admin RBAC, session list/revoke-all UI, password-change flow, Google unlink, MFA, self-service deletion/export or retention policy enforcement for registered listeners. There is no comprehensive CSP/security-header policy, security event log or abuse monitoring. Rate limits rely on correct proxy identity: `render.yaml` does not declare `TRUSTED_PROXY_CIDRS`; shared proxy IP buckets may throttle unrelated visitors. Do not fix this by blindly trusting forwarding headers. A new public proxy-chain/rate test is required before broader release. No penetration test, browser compatibility certification or production security claim is supported.

## 5. Redis, caching and rate limits

**Classification: IMPLEMENTED BUT NEEDS HARDENING.** [redis.js](../server/infrastructure/redis.js), [catalog repository](../server/repositories/catalog.js), [seed.js](../server/database/seed.js), [catalog import](../server/catalog/import.js), [HTTP middleware](../server/middleware/http.js), [redis tests](../server/test/redis.test.js).

- Cache-aside neutral story/list/genre payloads, 60-second TTL, revision-based invalidation in the same transaction as known catalog writes. Authoritative revision is read from PostgreSQL; favorites overlay comes from the current user's DB. Recommendations reuse catalog caching but their personalized response is not globally cached.
- Per revision, 128 hashed slots bound search-key growth; full hashes prevent incorrect responses on collisions. Counters measure hits/misses/errors/writes per API process, not a global metrics service. Revision churn can temporarily retain multiple generations until TTL; values/list sizes are not bounded by pagination.
- Atomic Redis Lua `INCR/PEXPIRE`: general API 300/IP/minute, auth writes 15/IP/15 minutes, targeted supplied-email bucket 10/15 minutes. Range streams/HEAD are exempt. Separate-instance shared-limit and forged-forwarding-header tests passed.
- Redis failure: catalog/discovery uses PostgreSQL and a bounded process-local limiter; auth/private JSON fails closed with 503; audio remains usable. Recovery was tested by stopping/starting **only the new audit Redis**. Without configured Redis, limits are intentionally process-local.

Gaps: fixed windows can burst at boundaries, local fallback is not distributed, no account-targeted subject bucket for Google credentials, public/analytics/normal writes share the general budget, no cache single-flight/stampede guard, no negative-cache policy review, and shared cache/queues/limits compete for a 64 MB noeviction budget in Compose. Direct SQL catalog edits bypass revision invalidation unless the operator advances it. Do not claim Redis makes every query faster; measured results are linked below.

## 7. Streaming, offline, analytics and discovery

**Streaming: COMPLETE AND VERIFIED for the current public catalog.** Bundled WAV delivery streams from a file descriptor with exact 200/206/416, suffix/open/clamped ranges, HEAD, ETag/If-Range and abort cleanup. Numeric IDs resolve DB-approved real paths under the fixed root, including symlink checks. External MP3s use approved Archive redirects; SoundWave does not own/cache/transcode those bytes or guarantee their availability. External HEAD uses imported size metadata. [stream tests](../server/test/stream.test.js), [catalog tests](../server/test/catalog-import.test.js).

**Offline: IMPLEMENTED BUT NEEDS HARDENING.** Production-only registration and build-generated shell hashing are in [OfflineContext.jsx](../client/src/OfflineContext.jsx), [sw.js](../client/public/sw.js), [vite.config.js](../client/vite.config.js). Explicit public downloads accept WAV/MP3, validate length/signature, admit ≤25 MB/chapter and ≤200 MB/device, handle quota/registration errors and support offline 206/416 seeking/removal. Private sessions/library/progress/analytics never enter persistent SW caches. No offline identity restoration/private-write sync exists. Limits are tab-local admission checks rather than a cross-tab atomic quota; full responses/range slices allocate buffers, stale public metadata has no explicit reclamation, browser eviction is possible, and a dishonest Content-Length can exceed pre-buffer expectations before validation. These are hardening items, not creator-upload support.

**Analytics: IMPLEMENTED BUT NEEDS HARDENING.** [PlayerContext](../client/src/PlayerContext.jsx) measures online wall time, flushes intervals, excludes seeking/buffering, and bounds intervals; [listening repository](../server/repositories/listening.js) generates favorites/completions transactionally; [analytics routes](../server/routes/analytics.js) reject invalid/conflicting events. Repeated identical UUIDs and repeated completion PUTs do not duplicate transitions. Tests verify seek distance is excluded and totals survive restart. Completion counts represent current completed progress rows, not lifetime unique listeners. Independent concurrent playback devices/tabs can count overlapping real wall time; clients can manufacture new valid event UUIDs, and failed playback telemetry is dropped rather than retried durably. No billing-grade/fraud-resistant metrics, offline analytics replay or platform-wide creator reporting exists.

**Search/recommendations: PARTIALLY IMPLEMENTED relative to mature discovery.** Title/genre literal substring SQL search, exact genre filter, deterministic sorting; `newest` means descending story ID, not publication time; `trending` uses seeded/imported popularity, not measured rolling engagement. Recommendations score favorite genres +4 and distinct listened-story genres +2, exclude favorites/completed stories, tie-break by popularity/ID and return four explanations. [discovery.js](../server/services/discovery.js). No full-text relevance, typo handling, language/tag facets, recency decay, quality evaluation, embeddings, LLM or behavioral model. Rule-based personalization is real and explicitly labelled.

### Measured performance, with scope

The repository microbenchmark made 100 sequential reads per mode over six stories: uncached p50/p95 **0.538/0.797 ms**, warm Redis **0.677/1.032 ms**. Cache overhead dominated this small query.

The HTTP benchmark made **500 requests per run at concurrency 10**, two alternating repeats per catalog size, with response-digest consistency checks. All **4,000 responses matched, zero errors**. Auth/general middleware was present, but its rate budget was raised through the local test factory; these numbers do not measure the public limiter or real-user throughput. ## 11. Ranked gaps and release gates

1. **Creator identity and object ownership:** separate roles and resource owner relations; all creator/admin mutations require permission tests.
2. **Story/chapter Studio CRUD:** drafts, validation, stable IDs, optimistic concurrency and non-destructive archive behavior.
3. **Secure upload and owned media storage:** validated/quarantined files, quotas, object store, bounded processing and authorized URLs; existing public-file parser is not an upload boundary.
4. **Publishing and moderation:** explicit state machine, review/reject/unpublish, public visibility and cache/offline policy.
5. **Named playlists and editable cross-story queue:** favorites and chapter order do not supply these features.
6. **Profile, preferences and history controls:** editable identity-safe settings, paginated history, retention/deletion/export.
7. **Cross-device synchronization:** explicit conflict policy, versions and foreground refresh; current persistence alone does not synchronize simultaneous players.
8. **API contracts, pagination and CI gates:** bounded collections, stable errors/order, OpenAPI and repeatable clean test/build/migration checks.
9. **Operational durability and observability:** correct proxy identity, visible queue failures/lag, metrics/logs, durable worker/Redis and verified scheduled backups/recovery.
10. **Discovery quality and notifications:** full-text ranking/publication dates, measured rule-based relevance, follows/new-release notifications; optional AI only after evaluation and privacy/cost controls.

No local implementation work is BLOCKED. External email deliverability, Google provider-owner changes and any new public release need owner/provider configuration/approval; creator hosting/storage and moderation policy require decisions before release. Those dependencies do not justify adding placeholder endpoints or claiming completion.

**Smallest next deliverable:** private named-playlist CRUD with owner isolation and a simple library UI, reusing sessions/CSRF/repositories. Exclude queue editing and creator work from that first slice. [M1.2 acceptance criteria](SOUNDWAVE_V3_ROADMAP.md#smallest-m1-deliverable) define the concrete completion gate.
